ADR-004: 存储引擎选型——RocksDB（M1, v2.0-FP）¶

  • 日期：2026-10-07
  • 状态：已接受
  • 决策者：OpenXDB 项目（M0-lite 实验结论 → M1 正式开发）
  • 关联实验：E1 存储引擎基准实验记录

背景¶

M0-lite 阶段需为 OpenXDB 选定单机存储引擎。候选两条路线：

  1. RocksDB（C++，经 cgo 静态链接桥接入 Go）
  2. 自研内存 B+Tree（纯 Go，pkg/storage/btree）

项目定位：教学/实验性质的单机关系型数据库内核，最终演进为分布式数据库；商用目标为技术招牌 + 内容 + 代运维载体。

决策标准¶

标准 权重 说明
持久化与崩溃恢复 高 数据库内核的第一性需求，WAL 之外的最终落盘保障
成熟度与稳定性 高 商用招牌必须可对外演示，不能频繁丢数据
维护成本 中 单开发者项目，构建链路越简单越好
吞吐表现 中 实测数据支撑，但不单独决定选型
演进式开源路线 中 从单机长出来的分布式数据库：LSM/分区/SST 复用潜力
Go 主体 低 教学价值：核心逻辑仍以 Go 编写，cgo 仅限存储桥

备选方案评估¶

A. RocksDB（cgo 桥）¶

  • 吞吐（E1a，100 万 key，未开 fsync）：顺序写 961,538 TPS / 随机写 186,498 TPS / 随机读 71,003 QPS（P99 60 us）。
  • 持久化：SST + MANIFEST + WAL，自带崩溃恢复与压缩。
  • 成熟度：生产级引擎，社区与文档完善。
  • 代价：cgo 构建复杂（Windows 静态链接需 -lshlwapi -lrpcrt4 -lws2_32，C++20）；维护一层薄 C++ 桥（pkg/storage/rocksdb）。

B. 纯 Go 内存 B+Tree¶

  • 吞吐（E1b，同口径）：顺序写 1,043,841 TPS / 随机写 406,339 TPS / 随机读 613,497 QPS（P99 0 us）。随机读快近 9 倍。
  • 持久化：无。需自行实现落盘、恢复、WAL 复用，且内存结构上限决定数据规模受限。
  • 维护成本：纯 Go 低，但自研数据结构正确性风险高（本轮已修复 merge/borrowLeft 两个不变量缺陷）。

C. 纯 Go LSM（Pebble 类）¶

  • 吞吐与持久化均衡，社区成熟；但引入第三方 Go 引擎会削弱"从零实现"的教学价值，且未来分片/复制仍需抽象适配。

决策¶

采用 RocksDB（cgo 静态链接）作为 OpenXDB 的存储引擎。

理由：

  1. 持久化与崩溃恢复不可妥协：B+Tree 吞吐优势（随机读 8.6 倍）本质来自"不落盘"，无法弥补数据库最基本的数据安全承诺；RocksDB 的 SST/MANIFEST 体系直接满足恢复需求。
  2. 成熟度支撑商用目标：生产级引擎可对外演示与代运维背书，自研存储的崩溃风险不适合作为招牌。
  3. 演进路线复用：RocksDB 的 LSM/SST/分区能力与"单机长出来的分布式数据库"路线天然衔接，M2 复制 / M3 分片可在存储层之上叠加，无需重写引擎。
  4. 教学价值保留：Go 侧保持存储抽象（storage.Storage）、Key 编码、事务、SQL 全部自研；cgo 桥仅封装 Put/Get/Scan/WriteBatch/Snapshot，职责边界清晰；B+Tree 保留为对照参考与内存引擎实验。

后果¶

正向：

  • 开箱即得的落盘、压缩、缓存与成熟恢复机制。
  • 基准数据可直接进 README/博文，增强技术招牌说服力。

负向：

  • 构建依赖 C/C++ 工具链与 RocksDB 静态库，Windows 下需固定英文路径工具链。
  • cgo 桥需随 RocksDB API 演进维护（如 v11 DB::Open 改 unique_ptr）。
  • B+Tree 对照引擎保留在 pkg/storage/btree，仅供实验，不承担生产路径。
